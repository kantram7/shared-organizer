[ ] ANALYTICS — Продуктовая аналитика
Цель: на основании реального использования проверять востребованность функций, обнаруживать неудобные сценарии и скрытые потребности, оценивать эффект изменений. В частности: часто используемая функция может быть спрятана глубоко в интерфейсе, а заметная функция — почти не использоваться.
- Firebase Analytics + экспорт событий в BigQuery, отдельные аналитические витрины (сессии, последовательности действий, использование функций, UX-издержки, техническое качество). Единый Analytics Service с контрактами событий, параметрами, версионированием, контролем качества данных.
- События: открытие экрана/функции и источник перехода; открытие, сохранение и отмена редактора; смена значений по умолчанию; действия с приглашениями; поиск (число результатов, без текста запроса); отправка и открытие уведомлений; ошибки синхронизации; перетаскивание; завершение задач.
- Метрики: частота полезных действий, глубина и длительность навигации, время создания записи, отмены, переходы между разделами, использование настроек, время ответа на приглашение, доля успешных действий, DAU/WAU, ошибки. Частота использования × лишние действия — ориентир для приоритизации UX, а не самостоятельное доказательство проблемы.
- Раздельно анализировать сценарии двух участников с их согласия, различать версии и каналы сборок. Не отправлять содержание сообщений, заметок, заголовков, поисковых запросов и персональные данные; идентификаторы пользователей псевдонимизировать. Предусмотреть выключение телеметрии. Не считать повторные действия независимой выборкой пользователей и не заявлять статистически значимые A/B-тесты при n=2.
- Желательно начать сбор базовой телеметрии до крупных UX-изменений. Сравнивать до/после релиза, дополнять наблюдениями и обратной связью. Низкая частота не означает ненужность функции, а отсутствующая функция напрямую не наблюдается.
- Проверки: DebugView, экспорт, полнота/дубли, версии контрактов, отсутствие чувствительных данных, отключение сбора, исключение демо и тестовых событий из рабочих отчётов.

[ ] UPDATE — Самообновление приложения и два канала релизов
Цель: отказаться от ручной пересылки и установки APK при каждой сборке. Использовать Firebase Storage и Remote Config либо подписанный HTTPS-манифест. Update Manager не привязывать жёстко к Firebase, чтобы в будущем можно было сменить сервер распространения.
- При запуске и периодически в фоне проверять актуальную версию своего канала. Скачивать APK в фоне, возобновлять при сбоях, показывать прогресс, список изменений и возможность установки. Опционально только Wi-Fi, автообновление по настройке. Использовать системный PackageInstaller; бесшумная установка лишь при выполнении условий Android, иначе системное подтверждение. Не прерывать редактирование/отправку сообщений без необходимости.
- Два канала: beta (владелец проекта получает новые сборки первым, проверяет их на своём устройстве) и stable (второй участник получает только проверенные и явно одобренные сборки). По умолчанию stable. Канал назначается по авторизованному аккаунту/устройству; доступ к тестовым APK ограничен правилами Storage. Возможность переключения — только осознанно, с учётом ограничений понижении versionCode.
- Процесс: собрать и подписать APK, прогнать тесты и lint, опубликовать в beta, проверить на устройстве, затем явным действием продвинуть тот же проверенный артефакт в stable без пересборки. Не продвигать beta автоматически. Сохранять changelog и статус релиза; логировать успешность скачивания/установки без чувствительных данных.
- Сохранять applicationId и совместимый сертификат подписи, строго увеличивать versionCode; проверить совместимость данных между версиями. При возврате с beta на старый stable не пытаться принудительно понизить версию: дождаться совместимой stable или выпустить исправленную сборку с большим versionCode. Не удалять приложение и данные ради обычного обновления. При проблемах предусмотреть остановку распространения и исправляющий релиз.
- Манифест: канал, версия/versionCode, минимальная поддерживаемая версия, URL/путь, размер, SHA-256, changelog, обязательность, подпись. Проверять подпись манифеста, целостность APK, пакет и сертификат; ключи подписи не хранить в Storage, Git или APK. При недоступности сервера продолжать работу на установленной версии; обязательные обновления только при реальной необходимости. Отдельный бюджет и правила доступа к хранилищу релизов.
- Проверки: beta недоступна стабильному пользователю, ручное продвижение идентичного APK, несовместимые версии и подписи, повреждённый файл, потеря сети, перезапуск, отказ от установки, сохранение данных и аккаунта, обновление на физических устройствах. Стабильный и тестовый каналы сборок должны сохранять совместимость API/Firestore; риск тестирования на реальных данных учесть отдельно.
