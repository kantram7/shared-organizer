1. ЗАФИКСИРОВАННОЕ РЕШЕНИЕ

Основной формат текста — Markdown с небольшим согласованным расширением
<u> для подчёркивания. Базовый синтаксис Markdown дополняется чек-листами
и зачёркиванием из GFM. JSON с отдельным деревом стилей не является основным
форматом содержимого. Это уточнение заменяет прежнюю рекомендацию хранить
текст как структурированный JSON-документ.

Пользователь работает в визуальном редакторе: пишет обычный текст,
выделяет фрагмент, выбирает стиль и видит результат без служебных маркеров.
Прямой ввод поддерживаемого Markdown тоже доступен.

Общий движок и одинаковые правила применяются к:
- заметкам;
- описаниям планов;
- описаниям задач;
- сообщениям во всех чатах.
В заголовках планов и задач набор оформления ограничен для компактности.
Одинаковый принцип не означает одинаковое число кнопок в каждом поле:
инструменты настраиваются по назначению поля.

2. ЧТО ЕСТЬ В ПРОВЕРЕННОМ КОДЕ ЗАМЕТОК

NotesStore.kt:
- NoteBlock хранит id, kind, text, checked, bold. Жирность относится ко всему
  блоку; типы: TEXT, HEADING, BULLET, NUMBERED, CHECK.
- Группы, заметки, исходящие записи и переносы лежат в одном локальном
  JSON-файле в noBackupFilesDir. Замена файла атомарная.
- changed() синхронно вызывает persist() при каждом изменении; сериализуется
  весь набор, NoteFile.write() вызывает fd.sync(). Это потенциальное место
  задержек UI; длительность не измерялась.
- Для облака уже есть очередь и задержка 500 мс. Общие заметки отправляются
  целиком; обычное редактирование не сравнивает исходную серверную ревизию.
  Такая проверка есть в переносе заметки.
- Личные заметки и их архив не отправляются в Firestore и историю записей.
- Поиск и карточки извлекают текст старых блоков.
- Есть ограничения по длине, числу блоков и размеру записи; часть текста
  сейчас ограничивается через take().

NotesScreen.kt:
- Каждый блок — отдельный BasicTextField со шестерёнкой.
- Курсор и выделение ограничены отдельным полем.
- Внизу постоянно показаны кнопки добавления всех видов блоков.
- lineHeight=28.sp дополнен отступами строк и блоков.

backend/firestore.rules, noteValid(): разрешён строго старый набор полей.
Переход на новую структуру требует согласованного обновления правил.
Схемы хранения описаний и сообщений перед реализацией общего редактора
нужно отдельно проверить; анализ текущего NotesStore не является их аудитом.

3. ИНТЕРФЕЙС И ДОСТУПНЫЕ СТИЛИ

Заметка: название и текст без рамок и шестерёнок у каждого абзаца;
клавиатура после нажатия в текст. Наверху — назад, меню и ненавязчивый
статус сохранения. Выделение должно работать между абзацами.

Меню выделения: стандартные действия и жирный, курсив, подчёркивание;
дополнительно зачёркивание, ссылка и очистка форматирования.
Компактная панель во время ввода: Aa, списки/чек-лист, undo, redo.
Форматирование меняет текущий абзац или выделение, а не создаёт пустой
блок в конце. Enter продолжает список; Enter на пустом пункте завершает его.
Смешанный текст и чек-листы остаются в одной заметке.

Для описаний планов/задач используется тот же принцип и компактный профиль
инструментов. Для сообщения — те же стили и правила Markdown с панелью,
соответствующей полю отправки; не копировать целый экран заметки в чат.

Заголовки планов/задач: короткий набор стилей. Предложение для макета:
обычный текст, жирный, курсив. Это ещё не утверждённый точный набор.
Не добавлять туда списки, многоуровневые заголовки, произвольные размеры
или цвета слов. На карточках, доске и в календаре не показывать Markdown-маркеры.

Первый объём для основного текста: B/I/U, зачёркивание, ссылка, очистка,
обычный текст, два уровня заголовков, списки, чек-листы, undo/redo.
Точный профиль сообщений и описаний проверить макетами. Изменение галочки
в отправленном сообщении — изменение содержимого сообщения и должно
подчиняться правам и существующему сценарию его редактирования.
Таблицы, вложения, каталоги шрифтов, палитры и перетаскивание блоков
не включаются автоматически в объём этой переработки.

4. ТИПОГРАФИКА ОТДЕЛЬНО ОТ ТЕКСТА

Семейство шрифта, базовые размеры, высота строки и поля задаются приложением
для конкретного вида текста. Они не записываются в Markdown каждого слова.
Цвет текста следует теме. Личный размер чтения — настройка устройства,
которая не меняет оформление общей заметки на другом телефоне.

Предложение для макета заметки: один шрифт с кириллицей (Inter либо системный
sans-serif), основной текст 16/24 sp, название 24/30 sp, подзаголовок 20/26 sp,
служебный текст 12–13/18 sp, поля 16 dp. Сравнить нынешние 28 sp с 24 sp.
Значения не утверждены и не должны автоматически переноситься на сообщения
или заголовки карточек: общий механизм допускает разные компактные стили.
Учесть системный масштаб и реальные начертания. Для первого этапа достаточно
небольшого набора размеров чтения вместо независимых регуляторов всего.

5. ХРАНЕНИЕ: MARKDOWN КАК ЕДИНСТВЕННЫЙ ИСТОЧНИК ТЕКСТА

Хранить исходную строку Markdown и признак её формата/версии. Пример имени
маркера для обсуждения: textFormat=markdown-v1; конечные имена зависят от
схемы заметки, описания и сообщения. Типизация нужна, чтобы не интерпретировать
старую обычную строку со звёздочками как новое форматированное содержимое.

Локальный JSON-файл и поля Firestore могут оставаться оболочкой для этой
строки и метаданных: id, группа, доступ, время, revision и т. п.
JSON как контейнер не означает JSON как дерево стилей документа.
Не хранить независимые постоянные копии одного текста в Markdown/HTML/JSON.
Внутреннее дерево редактора допустимо в памяти; восстанавливаемые кэши
превью допустимы, но не являются источником истины.

Состояния чекбоксов кодируются синтаксисом task list: - [ ] и - [x].
Оформление фрагментов: **жирный**, *курсив*, ~~зачёркнутый~~, <u>подчёркнутый</u>.
<u> — оговорённое расширение, а не обещание одинакового отображения во всех
сторонних Markdown-приложениях. Произвольный HTML не требуется.

Поиск, карточки, уведомления и компактные подписи должны использовать
извлечённый видимый текст или разрешённое оформление, без служебных маркеров.
Копирование в обычное поле передаёт видимый текст; экспорт .md — исходник.

Редактор обязан обеспечивать устойчивый цикл Markdown -> редактирование ->
Markdown -> повторное открытие для всего согласованного набора, включая
подчёркивание и галочки. Не требовать побайтового равенства исходников,
если допустима нормализация: проверять содержимое, стили, структуру и смысл.
При неподдерживаемой конструкции сохранять исходник или предлагать безопасный
режим, а не автоматически заменять его урезанным результатом.

6. ЕДИНЫЙ АЛГОРИТМ РАБОТЫ С ТЕКСТОМ

1) Распознать формат записи. Старый plain text не парсить как Markdown.
2) Загрузить поддерживаемый Markdown во внутреннее состояние редактора.
3) Применять ввод/стили к этому состоянию, сохраняя курсор, выделение и undo.
4) Сериализовать изменения в Markdown на границе сохранения/снимка.
5) Отображать через общий парсер и профиль конкретного поля.

Не перезагружать редактор из Markdown при каждом символе: это сбивает курсор,
композицию клавиатуры и историю. Превращать завершённые конструкции в стиль
вне активной IME-композиции; действие можно отменить.
Подсказки и меню применяют тот же набор стилей, что поддерживает кодек.

Общий редактор не меняет жизненный цикл формы или сообщения:
- заметка сохраняется по согласованному сценарию автосохранения;
- описание сохраняется вместе со своей формой по её текущему сценарию;
- сообщение отправляется только явным действием отправки;
- автосохранение черновика сообщения не отправляет его;
- изменение сообщения доступно по существующим правам редактирования.

7. ДВИЖОК И ПРОТОТИП

Compose Rich Editor остаётся кандидатом, а не утверждённой зависимостью.
У проверенной модели есть обычные списки и стили, но нет отдельного типа
checklist с checked. Наличие Markdown import/export не доказывает поддержку
всего нашего подмножества и сохранность <u> при экспорте.
Нужен прототип: настоящие галочки, единое выделение между абзацами, B/I/U,
вставка Markdown, undo/redo, повторное открытие и совместимость с проектом.
Наш проект: Kotlin 2.2.21, Compose BOM 2025.10.01. Совместимость с выбранным
опубликованным релизом проверяется отдельно; main не равен версии релиза.

Cascade Editor имеет todos и конфигурируемый интерфейс, но нативное выделение
по README остаётся внутри одного блока, а Markdown-кодек experimental.
Это существенные компромиссы, которые не снимаются скрытием панели.

Выбрать самый небольшой готовый движок, закрывающий согласованные сценарии.
Не принимать библиотеку, если ради неё нужны глубокий форк, потеря галочек
или возврат прежнего неудобного выделения по отдельным полям.

8. СОХРАНЕНИЕ, СИНХРОНИЗАЦИЯ И КОНФЛИКТЫ

На первом этапе форматирование не требует новой БД или нового сервера.
Сохранить существующие границы приватности и прежние права.
Для заметок вынести сериализацию и fd.sync() из UI в последовательный
I/O-писатель. Более старый снимок не может заменить новый. Статус «Сохранено»
соответствует подтверждённой локальной ревизии, а не только вводу в память.
Уход с экрана/в фон должен завершать ожидающее сохранение; проверить аварийное
завершение отдельно. Не вводить незаметно длинную задержку локальной записи.
Если запись всего контейнера окажется дорогой по замерам, отдельно выбрать
файлы на заметку либо транзакционную БД; не внедрять обе системы заранее.

Для заметок сохранить облачную очередь и задержку около 500 мс.
Остальные сущности используют собственные сценарии сохранения/отправки.
У текстового редактора общий кодек, но нет самостоятельного разрешения
отправлять сообщения, менять доступ или сохранять чужие записи.

Для общих заметок при отправке сравнивать базовую серверную revision.
При конфликте сохранять локальный черновик восстановления и давать выбрать
серверную версию либо свою копию; не перетирать чужой текст молча.
Простой текстовый Markdown-merge не гарантирует корректность форматирования,
поэтому не считать его автоматическим решением конфликта.
Личные заметки и восстановительные черновики не публикуются автоматически.

9. МИГРАЦИЯ

- Новые клиенты различают старые обычные строки/блоки и новый Markdown.
- Конвертер старых заметок сохраняет порядок, архив, bold и checked, экранирует
  буквальные Markdown-символы. Многострочный checkbox не дробится на несколько
  независимых задач. Переносы строк проверяются на выбранном парсере.
- Названия, описания и сообщения, ранее не имевшие форматирования, остаются
  обычным текстом либо преобразуются с экранированием, без смены смысла.
- Подготовить локальную восстановительную копию с прежними правилами
  приватности; личные копии не отправлять в облако.
- Снимки pending writes и moves тоже содержат старый формат; не сбрасывать
  очереди и не запускать миграцию поверх незавершённого переноса.
- Правила Firestore для заметок, описаний, сообщений, переносов и удалений
  должны учитывать новый маркер формата и запрет понижения схемы.
- Сначала выпустить совместимых читателей на используемые устройства,
  затем включать запись нового формата. Старые офлайн-операции не должны
  затирать новое оформление. Одной игнорируемой старым клиентом метки мало.
- Миграция общих записей идёт с проверкой revision и без дублей.
- Ограничения длины и размера пересмотреть с учётом разметки; не обрезать
  Markdown молча посередине конструкции и не терять пользовательский текст.

10. ПОРЯДОК РАБОТЫ И ПРОВЕРКИ

A. Макеты заметки, описания, поля сообщения и компактного заголовка;
прототип движка на искусственных данных. Проверить выбор стилей и Markdown
round-trip, галочки, несколько абзацев, меню выделения, IME, кириллицу/emoji.

B. Общий профиль Markdown, кодек, формат-маркер и извлечение видимого текста.
Проверить вложенные/совмещённые стили, буквальные спецсимволы, ссылки,
переносы строк, неподдерживаемые конструкции, пустой текст и лимиты.

C. Интеграция по полям: заметки -> описания -> сообщения -> заголовки.
Сохранение и отправка остаются подконтрольны соответствующим экранам.
В карточках не создавать живые редакторы, использовать лёгкое представление.

D. Миграция, правила и проверки двух клиентов: офлайн, конфликт, архив,
личное/общее, права и старые очереди. Проверить, что форматирование сообщения
не отправляет его и не даёт менять чужой текст. Перед включением подтвердить
сохранность старых данных и восстановление после ошибки записи.

Этот документ фиксирует решение и дальнейшие проверки. Изменения кода,
облачных правил и APK в рамках фиксации не выполнялись.
